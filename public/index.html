Request guide Turn rough pressure into a clear issue.

The strongest submissions isolate one move, explain why it matters, and describe the user-facing shift instead of prescribing implementation line by line.

1

Name the move

Call out the specific feature, fix, or redesign you want instead of gesturing at a mood.

2

Explain the friction

Say what feels broken, bland, confusing, or slow so the agent can judge the real product problem.

3

Point to the outcome

Describe what better looks like, including constraints when they affect the shape of the change.

Example

Make the queue feel live by giving accepted, running, and rejected requests stronger visual distinctions and clearer timestamps so the public feed reads like active product work instead of a plain issue list.

The agent decides the best product move. Requests should argue for the outcome, not lock the implementation.

What the product rewards

Specific pressure travels farther than nice words.

OpenReactor is built to make decisions in public. Clear problem framing gives the agent room to choose a better implementation than the literal request when the product needs it.

Scope discipline

One request. One decision. One visible result.

The current loop is intentionally small: intake, GitHub issue creation, public queue visibility, and an autonomous local agent. Keep requests inside that operating envelope.
